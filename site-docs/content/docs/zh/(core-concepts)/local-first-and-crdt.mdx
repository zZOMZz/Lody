# Local First 与 CRDT

Lody 希望成为一个 Local First（本地优先）的 Coding Agent 工作空间。这个方向经常和“离线应用”“远程执行”或“自动合并代码”混在一起，但它们不是同一个概念。

先记住两个结论：

- **Local First**：本地数据和本地计算是主要工作入口，服务器用于同步、协作和跨设备连接。
- **CRDT**：多个数据副本被并发修改后，仍能自动合并并最终得到一致结果的数据结构。

CRDT 不替代 HTTP 或 WebSocket，也不替代 Git。它们分别解决不同层次的问题。

## 什么是 Local First？

传统的服务端中心应用通常把服务器数据库看作唯一真实数据：

```text
客户端读取数据 → 请求服务器修改 → 服务器确认 → 客户端刷新
```

Local First 应用则让本地副本先成为可工作的真实数据：

```text
本地读取和修改 → 立即更新界面并持久化 → 联网时同步 → 各副本收敛
```

这不意味着用户必须先离线工作，也不意味着服务器不再重要。正常联网时，变化仍然可以实时同步；区别在于一次本地操作不必总是等待服务器批准后才能成立。

### “本地”不一定是当前拿在手里的设备

在 Lody 中，本地通常指 **Agent 所在的执行机器**。例如，你可以从手机发出指令，但 Agent 实际运行在办公室的 Mac 上：

```text
手机上的 Lody
      │ 发送指令
      ▼
办公室 Mac 上的 Lody daemon
      │
      ▼
Codex / Claude Code → 修改 Mac 上的 Git 仓库
```

仓库、终端、Agent 进程和登录状态都留在执行机器上。手机承担控制和查看的角色，不会自动获得仓库的另一份完整副本。

## 什么是 CRDT？

CRDT 是“无冲突复制数据类型”（Conflict-free Replicated Data Type）。可以把它理解为一套预先定义好的合并规则：不同设备可以先修改各自的数据副本，之后以不同顺序收到更新，最后仍然得到相同结果。

CRDT 保证的是 **收敛**，也就是“大家最终看到相同的数据”，而不是“系统能猜出人真正想要什么”。

### 示例一：同时修改不同字段

Alice 和 Bob 都看到了同一个 Session：

```text
标题：修复登录问题
状态：进行中
```

随后两人同时操作：

- Alice 把标题改为“修复 OAuth 登录问题”；
- Bob 把状态改为“已归档”。

如果客户端向传统接口提交整个旧对象，后一次保存可能覆盖前一次保存。CRDT 会把它们保留为两个独立更新：

```text
Alice：修改 title
Bob：修改 archived
```

同步后，双方都可以得到：

```text
标题：修复 OAuth 登录问题
状态：已归档
```

### 示例二：同时向列表添加内容

假设 Alice 和 Bob 都处于离线状态，并分别向任务列表添加项目：

```text
Alice 添加：检查失败的测试
Bob 添加：更新迁移文档
```

重新联网后，CRDT 列表可以保留两个插入操作，并让所有副本以相同顺序显示它们，而不要求其中一人先撤销并重新提交。

### 示例三：同时修改同一个字段

如果 Alice 和 Bob 同时把标题改成不同内容，CRDT 会按照数据类型定义的稳定规则选出或表示一个结果，确保所有副本一致。

但 CRDT 不知道哪个标题更符合团队意图。对于这种业务冲突，用户仍然可能需要讨论并再次修改。CRDT 解决的是数据合并和一致性，不是所有协作分歧。

## CRDT 与 HTTP、WebSocket 有什么区别？

它们不在同一层：

- HTTP、WebSocket 和 Loro Streams 解决 **更新如何传输**；
- CRDT 解决 **更新到达后如何合并**。

CRDT 更新完全可以通过 HTTP 或 WebSocket 传输：

```text
CRDT 更新
   ├── HTTP
   ├── WebSocket
   ├── Loro Streams
   └── 本地 IPC
```

| 方面 | 传统服务端中心模型 | CRDT / Local First 模型 |
| --- | --- | --- |
| 数据权威 | 服务端数据库 | 多个可合并的数据副本 |
| 本地修改 | 通常等待服务端确认 | 可以先写入并持久化到本地 |
| 离线修改 | 需要额外设计 | 是数据模型的核心场景之一 |
| 并发冲突 | 覆盖、拒绝或手工合并 | 按 CRDT 规则自动合并并收敛 |
| 重连 | 重新拉取服务端状态 | 交换缺少的更新 |
| 一致性 | 服务端确认更直观 | 通常是最终一致 |

服务器在 CRDT 架构中仍然可以负责身份认证、权限控制、持久化、消息转发和设备发现，只是不必成为每一次普通数据修改的唯一裁判。

## Lody 中哪些内容由什么机制管理？

理解 Lody 时，最重要的是把“工作空间状态”和“仓库代码”分开：

| 内容 | 主要机制 | 说明 |
| --- | --- | --- |
| Session 消息、状态和工作空间配置 | Loro / Flock CRDT 文档 | 在相关客户端和运行时之间同步协作状态 |
| Agent 运行、终端和工具调用 | 执行机器上的 CLI / daemon | 发生在 Session 绑定的机器上 |
| 仓库文件和代码改动 | 本地文件系统、Git 和 worktree | 不由 CRDT 自动合并源代码 |
| 分支之间的最终整合 | commit、merge、rebase 或 PR | 继续使用标准 Git 工作流 |

所以，“CRDT 自动合并”通常指消息、配置或状态，而不是把两个 Agent 对 `app.ts` 的修改自动揉成一份正确代码。

## Alice 和 Bob 如何一起使用 Agent？

### 继续同一个 Session

Alice 在自己共享的机器上创建 Session 后，Bob 向这个 Session 继续发送指令：

```text
Bob 的客户端
      │ 追加指令
      ▼
Alice 机器上的同一个逻辑 Session
      │
      ▼
原 Agent 配置 + 原工作目录或 worktree
```

此时，指令仍然在 Session 绑定的机器上执行。Bob 使用的是 Alice 机器上的 Agent 配置和执行环境，而不是因为消息来自 Bob 就自动迁移到 Bob 的机器。

这要求 Bob 有权访问该 Session 和机器，并且 Alice 的机器在线。机器离线时，其他设备无法远程驱动上面的 Agent。

### 创建另一个 Session

Bob 也可以在自己的机器上创建独立 Session 和 worktree：

```text
Alice 的 Session / worktree ─┐
                             ├── Git branch / PR → 合并代码
Bob 的 Session / worktree   ─┘
```

两个 Session 的对话和执行环境彼此独立。团队可以共享它们的状态和 Diff，但最终代码仍然通过 Git 合并。

## 断网后会怎样？

Local First 的目标是让已有的本地能力尽量继续工作。例如，执行机器短暂断网时，不依赖网络的本地进程和操作仍可使用本地仓库，已经落盘或可以持久化的状态可以留在本地；重连后，再同步缺少的 CRDT 更新。

它不能消除真实的网络依赖：

- 手机无法实时控制一台完全离线的电脑；
- 团队成员暂时看不到尚未同步的新进展；
- 依赖在线模型 API、GitHub 或远程 MCP 服务的操作仍会失败或等待；
- 远程指令无法在机器不可达时立即执行。

因此，Local First 不等于“任何功能都能离线使用”，而是让本地已有的数据和计算不因中心服务暂时不可用而全部失效。

## 它和 SSH 有什么关系？

SSH 解决的是“如何安全地登录并操作另一台机器”，Local First 解决的是“本地副本如何工作，以及多台设备如何同步协作状态”。

通过 SSH 在远程服务器上运行 Codex，同样可以让仓库和 Agent 留在那台服务器上。但 SSH 本身不提供共享 Session、CRDT 数据合并、多人状态同步或跨 Agent 调度。两者可以组合使用：SSH 用于机器运维，Lody 用于组织机器、Agent 和团队协作。

## 优点与代价

Local First 和 CRDT 的主要优点包括：

- 本地操作响应快，不必为每一步等待网络往返；
- 网络短暂中断时，本地能力仍可继续工作；
- 多设备和多人并发修改更容易自动收敛；
- Agent、仓库和凭证可以留在用户控制的机器上；
- 同一个工作空间可以逐步扩展到更多协作内容。

相应的代价包括：

- 同步、权限和文档生命周期更加复杂；
- 删除、压缩、垃圾回收和 Schema 迁移需要专门设计；
- CRDT 通常提供最终一致，而不是每一步都由中心事务确认；
- 数据结构可以自动收敛，但业务语义冲突仍需用户处理。

对于支付、库存等要求单一权威和强事务约束的数据，传统服务端数据库通常更直接。对于 Lody 这种本地执行、多设备访问、长时间 Agent 任务和团队协作并存的工作空间，Local First 和 CRDT 更符合它希望支持的使用方式。

Lody 仍在走向完整的 Local First 支持，因此这里描述的是产品和架构方向，并不表示当前每项功能都已经可以完全离线运行。
