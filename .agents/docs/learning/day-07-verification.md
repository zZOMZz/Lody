# 第 7 天：测试、定位与综合作业

[上一章](day-06-worktree.md) · [课程首页](README.md) · [答案与评分](answers.md)

目标：用陌生场景检验迁移理解，完成一个边界清楚的小改动。先修：前六天练习；用时约 180 分钟，桌面首次构建另留时间。

## 把“知道概念”变成“能给证据”

假设切换会话后界面突然出现旧正文。不要先去改 CSS，也不要直接归因于 CRDT。先描述可观察现象：哪个会话、哪个 Turn、什么操作顺序、何时出现错误。然后按层排查：数据已错、reader 接收了旧结果、投影映射错、还是组件展示错？

保留最小证据：合成输入、明确顺序、期待状态、实际状态。找到 reader 返回旧值，就不必为最小回归启动真实 Agent；问题只有在 preload/renderer 生命周期中出现时，仅测纯函数也不够。

| 层级         | 适合证明什么                               | 项目入口                                                                              |
| ------------ | ------------------------------------------ | ------------------------------------------------------------------------------------- |
| 纯决策       | 给定状态应做什么                           | [dispatch logic 测试](../../../apps/cli/src/session/session-dispatch-logic.test.ts)   |
| 数据边界     | 拒绝后状态不变，兼容内容不被破坏           | [HistoryWriter 测试](../../../packages/shared/tests/history-writer.test.ts)           |
| 受控异步集成 | 重连、乱序、资源释放                       | [本地传输回归](../../../packages/shared/tests/local-loro-transport-bug-repro.test.ts) |
| 桌面 E2E     | main/preload/renderer/CLI 一起完成用户操作 | [E2E 指南](../../../e2e/README.md)                                                    |

测试替身不是越少越好，也不是越多越容易测。替换不可控的网络和时间，保留你需要证明的真实边界。断言最终文档、可见状态、资源释放结果；“某 mock 被调用一次”通常不足以证明业务结果。

## 确定性测试的三个动作

1. 用手动 Promise/Deferred 等显式信号卡住某一步，不猜它需要多少毫秒。
2. 通过注入的时钟或 fake timers 推进时间，验证 deadline 前后行为；读 [Vitest timers](https://vitest.dev/guide/mocking/timers)。
3. 断言失败后仍可继续使用：旧状态保留、下一条合法输入可成功、取消不能复活终态。

第 3、5 天示例正是这种手动调度。它们不证明生产边界，但提供了设计测试顺序的方法。参考生产测试时，先写自己想观察的状态，再选择依赖替换方式。

## 综合作业：默认题与替代题

**默认题：补充 ConversationView 的一个行为回归。** 在现有 [reader 测试](../../../packages/components/tests/conversation-view-from-reader.test.ts) 内，先查已有 coverage，再挑一个尚未被覆盖的组合，例如“旧读取未完成时结构删除与租约释放相遇”。如果已有同等覆盖，不重复添加，改选一组不同且有意义的交错。

交付步骤：用合成 Turn 建 fixture；显式挂起读取；触发结构/内容变化或 release；让旧请求返回；断言最终 membership、正文和释放后的状态。若发现实现错误，做最小修复；若实现原本正确，可以只提交有效回归和解释，不能制造产品需求或编造缺陷。

**替代题：HistoryWriter 拒绝后的可用性。** 在既有套件增加一个未覆盖的非法字段组合，确认拒绝时既有 opaque 内容和已知字段均未受损，下一条合法命令可成功。先查看套件避免重复；不通过 string/regex 检查源码来“证明”行为。

在自己的学习分支完成，遵循变更范围的 `AGENTS.md`。证据使用合成数据；无需开 PR 到上游，也无需真实模型调用。

## 执行与记录验证

根据选题运行一个对应 suite：

```sh
pnpm --filter @lody/components exec vitest run tests/conversation-view-from-reader.test.ts
pnpm --filter @lody/shared exec vitest run tests/history-writer.test.ts
```

不是两个都必须运行。能安全做局部消融时，在个人分支暂时去掉你要保护的 guard，确认测试出现预期失败，再恢复 guard 并确认通过；保存原 diff，不能覆盖其他工作。无法消融时，写清这项证据缺失。

提交前按仓库要求执行：

```sh
pnpm check
pnpm format
pnpm run docs check
git diff --check
```

`pnpm format` 会修改文件，检查 diff 并排除与任务无关的格式变化。`pnpm check` 在前一步失败时会停止：typecheck 失败不能写成“测试全过”。依赖、子模块、系统工具未就绪时，把失败阶段记录清楚，不为通过门禁修改 unrelated 代码。

可选桌面验证先运行 `pnpm e2e:build`，再 `pnpm e2e:smoke`。它使用完整本地进程树及隔离状态目录。E2E 通过也只证明所执行的旅程；Scout 资源探索、真实账户和跨平台验收属于其他证据。

## 章末练习与毕业验收

- **7.1（2 分）** 为什么 `sleep(100)` 后断言容易产生假通过或偶发失败？用什么信号替代？
- **7.2（3 分）** 写出“发消息 → 执行 → 更新历史 → 界面订阅”的链路，并指出在哪一层区分 UI 接受、落盘、投递、执行完成。
- **7.3（5 分）** 为综合作业选择测试层级，解释替换了哪些依赖、保留了哪个真实边界，写一个失败后仍可使用的断言。

综合作业另计 20 分：问题与复现 4 分、源码因果链 4 分、最小改动 4 分、行为测试 6 分、限制说明 2 分。至少 16 分且关键边界解释正确才算通过。具体检查表和补救阅读见[第 7 天答案](answers.md#day-7)。

最终展示控制在一页：**问题、图/调用链、改变了什么、如何验证、没有证明什么**。能够向另一个开发者解释测试为什么会发现回归，比把测试数量增加一更重要。
